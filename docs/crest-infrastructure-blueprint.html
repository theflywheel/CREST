L1 · The layer that cannot bend

CREST Infrastructure Blueprint

The complete infrastructure-layer design: the objects, registries, contracts and invariants that must hold in every deployment for a decade — specified so that the configuration and product layers become thin, replaceable work on top. Substrate choices: Inji for the credential lifecycle, DeDi for tamper-evident public directories, CREST services for everything that knows about work.

1 · Scope and the L1 test

The actor-journeys model gives the admission test: if two deployments could reasonably disagree about it and both still be CREST, it is not infrastructure. Everything in this document passes that test — it is the set of things that must be identical everywhere so that a credential issued in one country verifies in another, a work definition means the same thing to every adapter, and a worker's guarantees hold regardless of which products a deployment runs.

Three substrates carry it. Inji (Certify, Wallet, Verify, eSignet) is the credential lifecycle — issuance, holding, presentation, verification. DeDi is the directory substrate — every registry whose records are public facts gets tamper-evidence, inclusion proofs, signed checkpoints and witnessing for free. CREST's own services hold what neither knows about: work, evidence, strength, consent, and personal data. Nothing below invents cryptography, wallets, or directory infrastructure.

2 · Object model: primitives and profiles

This table is canonical (#78); a section found still naming Qualification or ProjectGrant as a primitive is a defect to be fixed, not a reading to be reconciled: those two were collapsed into one Authorization at two scopes, and reading an older sketch literally rebuilds the twelve-primitive model this section removed — which came within one commit of happening while building the credential's issuer chain. An earlier draft put Worker, ProjectGrant and CompensationRecord in the core — the payments use case leaking into the layer that must outlive it. The strategy note's own warning applies: Aadhaar did not anticipate Jan Dhan; the core must not anticipate payroll. So the model is now two-tier: eleven generic primitives that know nothing about work or money, and profiles that instantiate them per domain. The generic pattern the primitives encode: a defined activity, an attested event, an owned claim, and trust derived from provenance.

3 · Registry architecture on DeDi

The ten registries split by one criterion: is the record a public fact or personal data? Public facts go on the deployment's DeDi node — append-only, inclusion-provable, checkpoint-signed, witnessable by peer nodes (including the global layer's node, giving cross-border verification a cryptographic rather than institutional basis). Personal data stays in the deployment's private store, in-country, forever.

Everything in this paragraph describes the intended arrangement, not the built one — a reader could not previously tell which half existed. The concrete cost today is that the skill list (§16) is deployment-local, so two deployments can mint the same code meaning different things with nothing to notice; and the witness ring's "neither can rewrite history unobserved" needs two nodes and has one. One DeDi node per national deployment, plus one global node holding only: deployment public keys, credential schemas, skill taxonomy, and signed work-definition mirrors (no personal data by construction — nothing personal is ever on any DeDi node). National and global nodes witness each other, so neither can rewrite history unobserved. DeDi-node's current operator-gated onboarding matches the org-onboarding default settled at G1 (§14, #6): a human approves, and the decision is a log entry rather than a row only the operator can see.

4 · Identity and the worker record

The worker record is deliberately minimal and the binding deliberately late:

  • Existence: a name and one contact route. No document, no phone, no literacy (W1). Assisted registration writes exactly the same record, marked with the registering agent's identity — it "counts the same" (W2) because there is literally no other kind of record.
  • Identifier: a pairwise, deployment-local did:crest:party:…. Pairwise so that presenting credentials never leaks a global correlatable identifier (W8). party, not worker, because §2 makes worker a role a Party holds and the fixture world already contains the case that breaks the narrower name: the same person working one project and supervising another. An identifier that names the role either misdescribes them or issues them a second id — the duplicate §4.1 exists to avoid (#55).
  • Identity binding: attached only when a credential first requires it, via eSignet as the single L0 interface (national ID / MOSIP / OTP behind one OIDC broker). CREST never talks to a national ID directly and never re-creates identity.
  • Deduplication: candidate duplicates are held, never merged; only the registry custodian merges, only with the worker's confirmation (W4). Merge is a private-store operation that re-points claims; issued credentials are untouched (they reference the surviving DID via a recorded alias).

4.1 · The identity-provider integration contract

"Binds to existing identity infrastructure" has to be a concrete interface, not a slogan. The contract has five parts:

Provider classes, like adapter classes

Identity providers are integrated once per class, configured per deployment — mirroring §8's evidence adapters. Four classes cover the target geographies: eSignet (MOSIP's OIDC broker — the preferred front door wherever a MOSIP or eSignet-fronted national ID exists), MOSIP IDA (direct authentication where eSignet isn't deployed), generic OIDC/eKYC (non-MOSIP national systems, e.g. eCitizen-style portals), and mobile OTP (the floor — proves control of a contact route, not legal identity). A deployment configures one or more providers; CREST core sees only the uniform interface below, never a provider's own API.

What CREST consumes, and what it stores

A binding event consumes a signed assertion and keeps three things only: an opaque subject reference (the provider's pairwise/pseudonymous subject identifier — with eSignet this is a per-relying-party PSUT, so CREST never holds a correlatable national ID), a salted hash of the national identifier for matching (below), and the assertion record (provider, class, assurance method, timestamp, expiry of validity if the provider states one). The raw ID number, biometrics, and demographic payload are never persisted — resolved at binding time, discarded after match. This closes the J12 gap ("whether CREST stores the raw ID number is unresolved"): it does not.

The pairwise partition is the relying party, not the OIDC client — confirmed against a deployed eSignet 1.8.0 (P0 finding E6, make spike-esignet). Two clients registered under one relyingPartyId receive the same subject for the same person; a client under a different one receives a different subject. Two consequences, both settled at registration time and silent if got wrong: every CREST client of a deployment must share one relying-party id, or one worker appears as two people; and two programmes that must not be able to correlate their workers must be registered as different relying parties. CREST requests name and phone_number only — never individual_id, which eSignet does offer (W9).

Identity assurance levels

Every worker record carries a derived identity assurance level, computed like tier strength — from facts, never asserted: IA-3 anchor-verified (biometric or eKYC against a national system), IA-2 document-seen (agent captured an ID document; checksum-valid but not authenticated online), IA-1 contact-verified (OTP on a reachable route), IA-0 asserted (name only, assisted enrolment). IA feeds the confidence score (S-3), duplicate detection (S-2), and — critically — the tier function of §6: Tier 1's stated primary risk is identity mapping error, so a Tier-1 outcome record claimed by an IA-0 worker resolves to a visibly weaker verdict than the same record at IA-3. Assurance and evidence strength stay separate axes; verifiers see both.

Matching: how evidence finds a worker

Source systems send whatever worker-joining identifier they have — national ID, phone, program roster ID. The resolution service (S-1) matches via the salted identifier hashes and registered contact routes, in declared precedence order, and records which key matched and at what confidence on the claim itself — provenance the tier function reads. No match → the unclear queue, never a silent guess. Roster IDs match only through a project-scoped mapping table loaded at project setup (L2 data).

Lifecycle: late binding, re-binding, migration

Binding is monotonic and late (W1): a worker starts at IA-0/IA-1, and attaching an anchor later retroactively upgrades the assurance read of already-issued credentials — no reissuance, because assurance is derived, not stored (same mechanism as J7's retroactive credentialing). Re-binding (new phone, re-issued national ID) appends a new assertion record; history is never rewritten. Anchor migration — a deployment switching providers, the J2 open gap — is now specified: bindings are per-provider records under a stable worker DID, so a new provider is added alongside the old, workers re-bind opportunistically at next authentication, and the old provider's assertions remain valid history rather than orphaned state. Inji Wallet's own activation uses eSignet directly where available; where not, wallet binding rides on the deployment's configured provider via the same interface.

Who may append a binding (#102, finding #123): self-proof — possession of the token whose subject is being bound — is accepted in exactly two shapes: a party with no identity bindings (the first-login bootstrap), or a party already bound to this same subject (the idempotent re-bind every login performs). Holding a valid token proves who the caller is, never that they are the party in the URL, so any other caller needs an act-for-party authorization — the door assisted enrolment uses. The accepted residual is stated rather than hidden: until its first binding lands, a party id functions as a bearer claim capability, tolerable because ids are unguessable ULIDs and enrolment binds promptly, and recorded as finding #123.

5 · Credential substrate on Inji

One credential type, one schema lineage, everywhere: WorkEventCredential, W3C VC issued by the deployment's Inji Certify over OpenID4VCI, signed with the deployment key (single-key custody per §14/D3 — the specifier/issuer split is structural in the data, cryptographic later if federation demands it).

Two references, one primitive (#78). qualificationRef and grantRef are the same Authorization at its two scopes — §2 collapsed the old Qualification and ProjectGrant into one object, and the names here are historical. They are kept because they are in the field set, and this note exists because reading them as two primitives led, once, to most of a twelfth primitive being built before §2 was re-read. Both always reference an organisation's authorization: a person's is never published (#68), so a chain ending at a supervisor ends somewhere a verifier cannot resolve — which is worse than ending nowhere, because it looks like it leads somewhere.

The confirmation block is an application annotation, ruled 2026-08-28 (#127). Which exit closed the window, and when, is a fact of the payments application — the first application built on this substrate — not of the credential substrate itself. Two deployments could run different confirmation policy, or none, and both still be CREST, which is §1's own test. The field stays in the shape because credentials already signed carry it and a signed document does not change; what changes is its standing: applications annotate credentials through this extension point, and the substrate neither requires nor interprets the block. A deployment with no payments application issues credentials without it.

Holding is Inji Wallet in three modes (mobile app; web at assisted-access points; printed PixelPass QR card, issued when a credential is issued rather than at enrolment) — same credential, no custodial wallet service. Both directions of the card format are now read (#92): Inji's library CBOR-wraps any JSON it is handed, so a card their wallet produced is CBOR inside, and CREST's decoder unwraps the JSON-compatible subset — refusing, by name, CBOR that JSON cannot hold, because a "successful" decode of bytes nobody expected was the failure shape the finding described. This previously read “from enrolment”, which cannot be right as written: at enrolment no work has been done and there is no credential to print. Settled 2026-08-24 (#24) — the card is produced at issuance, through the assisted-access channel enrolment also uses. An identity card at enrolment is a legitimate second artefact and is not this one; conflating them made the original wording read as though a worker walked away from registration already holding their work history.

Presentation is OpenID4VP online and PixelPass QR/NFC offline; the offline payload carries the full signed VC, so a bare scan verifies signature and schema with no network, and proves validity-at-issuance only (status needs signal — accepted, per the journeys' bare-scan semantics).

Format: eddsa-jcs-2022 — Ed25519 over JCS-canonicalised JSON (RFC 8785) as a W3C Data Integrity proof — day one; SD-JWT is the planned selective-disclosure upgrade and the schema above is field-compatible with it. Corrected from JSON-LD/Ed25519 (finding #60), for this section's own stated goal: verifying a JSON-LD suite needs RDF canonicalisation and a resolvable @context, and a verifier who must fetch a URL to check a signature is not the offline stranger §11 promises a minute to. The costs, accepted and written down in §14: interop is narrower than "a VC" implies, and canonicalisation must be exact — Go's default JSON marshalling HTML-escapes three characters RFC 8785 does not, found and pinned with a regression test; a canonicalisation bug is invisible to the system that has it, so only an outside implementation can find one.

Amended (finding #164, 2026-09-02): the suite above is the rule for CREST-issued credentials — window-exit issuance, the printed card, offline verification. The wallet path (Certify → Inji wallet → Inji Verify) signs Ed25519Signature2020 instead, because Inji Verify's verifier implements the 2018/2020 Ed25519 suites and no DataIntegrityProof suite: an eddsa-jcs-2022 credential answers INVALID there, proven empirically. Its RDF canonicalisation dereferences @context, so the credential's context is a document this deployment itself serves (apps/contexts/work-event-v1.json) with @vocab defined — load-bearing, since JSON-LD silently drops undefined terms and a dropped term is a field the signature no longer protects. The residual: each path's credential verifies only in its own stack's verifier; convergence (DataIntegrityProof upstream in Inji, or URDNA2015 in pkg/credential) is recorded in #164 rather than half-built.

Key custody, settled at G1 (#7). One issuance signing key per deployment, held by the operator. Per-organisation keys are deferred to federation, not rejected: they buy attribution and cost a custody lifecycle per organisation, and that trade is worth making when organisations sit across trust boundaries.

What the decision requires now is that custody stop being implicit. Implemented 2026-08-29 (#130): the issuance seed lives in a deployed Vault (Raft storage, private network only, operator-held unseal keys), and the one service that signs — verification, since #137 — fetches it at startup and refuses to start when Vault cannot answer, because a signer running on a key nobody escrowed is implicit custody wearing explicit custody's name. The signing key is never in the repository, never in an image layer, and no longer in a platform environment variable — a copy of a signing key is a signing key, and #65 already found a verifier key shipping inside a public image under a published password, which is the same mistake one component to the left. A compromise revokes every credential the deployment ever issued, because there is one key; that is the cost of the simple model and it is the reason rotation has to be a procedure somebody has rehearsed rather than a thing nobody has tried. #70’s instance record publishes the key id a reader should expect, so a rotation is observable and a move to per-org keys later is a mirroring problem rather than a reissuance one.

6 · Trust strength: facts stored, judgement derived

This resolves the contradiction between the concept note ("tier is a first-class property of every credential") and the journeys ("strength is never stored"). The rule, stated as infrastructure:

The credential stores provenance facts. The tier is a pure function, evaluated at presentation time: tier = f(evidence facts, definition@version's evidence-to-tier map, current source-assessment). It is always displayed — to worker and verifier alike — never written.

Consequences that make this the right L1 rule: re-assessing a compromised source system downgrades every affected credential's tier instantly, without reissuance; versioning a definition never strands old credentials (they resolve against their pinned version); no attester can inflate strength by asserting it — strength is derived from how evidence arrived, and transport never affects it. The function f itself is L1 (identical everywhere); the evidence-to-tier mappings are L2 data inside each definition.

Settled at G1 (#5): derived, with nothing on the credential. The concept note's reading was heard and not taken. A stored tier freezes a judgement verifiers should be free to make differently, and — the part that decided it — it cannot be raised when a worker binds an identity anchor a year later, so the worker who most needs their record to improve is the one it would be frozen against. Carrying the tier on the credential "as a convenience, clearly marked non-authoritative" was considered and rejected for the ordinary reason: the marked-non-authoritative field is the one every implementer reads.

Settled at G1 (#8): an external institution is institutional-system, and how its evidence arrived caps the tier independently. The open question was what class evidence carries when it comes from a hospital system, a training provider or a government programme that is not CREST-integrated — no adapter, no signed batch.

The answer keeps the two dimensions orthogonal, because they answer different questions. sourceClass names who the source is; captureMethod names how the record was produced. An unintegrated national hospital is institutional-system — that is what it is — and reaches Tier 3 only where its records are system-of-record: generated by the system in the course of its work. The same hospital's staff typing rows into a form is institutional-system with unsupervised-manual capture, and the letterhead does not raise it, because nothing about who an organisation is makes a hand-keyed row a system record.

Note what is deliberately not in that sentence: whether the batch arrived signed. Transport never affects strength (above), sourceExposure is carried and never read by f, and there is a test asserting it. A rule that let a signed upload raise a tier would let an attester inflate strength by choosing a channel, which is the exact failure §6's rule exists to prevent — and it would penalise the deployment that has to accept an emailed CSV from a hospital whose records are perfectly real.

Two alternatives were rejected for the same underlying reason: a new external-institution class, and demoting the unintegrated to programme-system, both encode how they integrated into a field that means who they are, after which the field can answer neither question. No new class and no change to f — and integrating that hospital later changes nothing about what it is.

A correction that came with #8. §8's credential sketch used to enumerate sourceClass as DHIS2 | HCM | COMMCARE | BATCH | … — product names. That cannot be right and the schema had already diverged from it: which vendor a record came from is not a trust property, it is a procurement fact, and a class list that names products has to be edited every time a country buys something. The enumeration above is now the one in schemas/primitives/.

7 · Work definition lifecycle

The definition is the object every other component reads, so its lifecycle is infrastructure even though its contents are pure configuration:

  • States: DRAFT → RATIFIED → ACTIVE → SUPERSEDED. Immutable from ACTIVE; every change is a new version; every version resolvable forever (a DeDi log entry, so this is enforced by substrate, not policy).
  • Separation of duties: author ≠ approver on the same version — an L1 rule, enforced in the definition service, not left to product UI.
  • Three faces, one signed record: worker face (plain-language evidence requirements + tier ceiling), platform face (source systems, required fields, outcome unit, tier map, schema pointer), verifier face (authorised issuer references, evidence-to-tier map, specifier signature, timestamp). One record, three projections — never three documents.
  • Payment set-ups link by reference, never embed: a definition is complete and usable with no rate attached, because recognition is a use of its own.

8 · Evidence ingestion contract

CREST absorbs heterogeneity; source systems change nothing. The L1 artefact is the canonical work-evidence record — what every class adapter must emit:

Field names are the deployment's, not the source's (#56, decided 2026-08-25). A tier map may require a field, and it names that field in the deployment's vocabulary; the adapter maps each source's own column names onto it from per-deployment configuration (Mapping: columns, enrichment renames, constants). The alternative — definitions naming fields per source — was rejected because it makes "source systems change nothing" quietly mean "…except the definitions that read them", and because its failure mode is the bad kind: a tier rule that never matches produces no error, only a credential resolved at the floor with every assertion passing. That is exactly how the finding was found. The cost, stated: a mapping that is wrong is a tier that is wrong, so mappings belong in the source-onboarding review next to the source assessment (§6).

mandatory core:            optional enrichment:
  activity                  geography (coarse only — raw location never stored)
  outcome { value, unit }   beneficiary counts, session metadata,
  workerJoiningIdentifier   supervisor identity, device attestation, …
  period { start, end }
  sourceExposure            # where/how the source exposes this record
provenance (adapter-attached, never source-asserted):
  sourceClass · captureMethod · adapterRef · receivedAt · sourceRecordRef

Rules that cannot bend: adapters are written per system class (one DHIS2 adapter, one CommCare, one HCM, one batch-file), configured per deployment; a record providing only the core is valid Tier-1-capable evidence; the four transports (push API, consent-triggered pull, signed batch, supervised manual upload) never influence strength; provenance is attached by the adapter and validated by the pipeline — whatever the source asserts about its own trustworthiness is ignored. The adapter registry (DeDi) records which adapter versions are recognised, so a verifier can walk evidence back to a known translator.

9 · Consent, confirmation, withdrawal

Consent happens exactly three times, and the three moments are distinct objects, never collapsed:

  1. Enrolment consent — the right to fetch and hold evidence about the worker. Recorded once per programme, revocable; voice recording is a valid capture for non-literate workers. “Recorded once” means once per relationship, not once per person: a worker who agreed to one programme holding their work history has not thereby agreed to every other organisation on the same deployment holding it, and nobody asked them that. Joining a second programme is a second question. Corrected 2026-08-24 (#24), after the first implementation scoped it deployment-wide. Withdrawal has effect rather than being a flag — identity resolution reports it and the evidence pipeline stops recording new work for that worker in that programme — but it never reaches backwards: work already recorded stays, and a confirmation window already open still exits and still releases payment. Consent governs what may be collected next; taking away the record, or the pay, for work already done would make withdrawal a penalty for exercising it.
  2. Issuance confirmation — is the draft record true? Draft credential → notify (SMS/USSD/supervisor-assisted) → confirm, dispute, or auto-confirm when the window closes. The state machine belongs to the payments application and the window's length is L2 configuration — seven days in the CHW programme, and T=7 anywhere in this document reads as that programme's setting, never as an infrastructure constant (ruled 2026-08-28, #127). What is not configurable is the contract: the window is bounded, every route out of it leads to issuance, and every exit releases payment; the credential flow can never block payment indefinitely.
  3. Disclosure consent — who may see what, per presentation. Showing the bare QR is itself consent for the non-identifying payload; anything more requires an explicit, scoped, recorded grant naming who asked and why. Enforced by the verification service, recorded in the private consent store.

Batch verification, settled at G1 (#9): capped, on its own authorization scope, and every check reaches the worker's audit trail. Disclosure consent above is per presentation, which answers the single-check case and says nothing about the thousand-check one. Uncapped, a verifier with a pass is a surveillance instrument: a lender or an employer could sweep a population and learn who has been working, where, and how recently.

Three rules, and the third is the one that carries the others. A per-pass rate cap, whose number is configuration and whose existence is not — two deployments may reasonably differ on the rate and neither may turn it off. A distinct authorization scope for bulk checking, so acquiring the ability to sweep is a decision somebody makes and can be seen to have made, rather than a capacity that comes free with an ordinary verifier pass. And every check in the worker's audit trail regardless of how it arrived (W8) — which is the rule that makes the other two auditable rather than merely asserted.

Audit-without-a-cap was considered and rejected. It makes sweeping observable rather than impossible, and a worker who can see they were swept and cannot refuse it has been given a receipt, not a control.

A dispute is metadata on the credential, never a revocation (#58). A claim can go ACCEPTED → DISPUTED after a credential was signed — it must, because the seven days are a window for objecting rather than a deadline for noticing — and neither §5 nor §9 previously said what happens to the credential when it does.

Nothing happens to it. A credential is a historical statement: what was asserted, by whom, and when. Revoking it because the worker later objected would mean a worker who disputes one detail — "it was six, not nine" — loses the whole record of work they did do, which is a penalty for objecting that falls on exactly the person the dispute exists to protect. So valid and contested are separate answers to separate questions: whether this issuer really asserted this and has not withdrawn it, and whether somebody says the underlying record is wrong.

The dispute is visible beside the credential rather than inside it — a signed document cannot carry a fact that postdates its signature — so a verdict reports the standing of every contest against the credential or the claim it names. Standing only: never the reason and never who raised it, because a dispute reason is ordinarily the worker speaking about their own record and a verifier’s legitimate interest is that the record is contested, not what was said about it.

The limitation this leaves, stated rather than discovered. A contest is resolved at verification time from the deployment that holds it, so an offline verifier — the bare QR scan §5 treats as a first-class case — sees a valid credential with no indication it is disputed. The status list has the same shape and §5 already accepts it ("proves validity-at-issuance only; status needs signal"), and a dispute is strictly newer news than a withdrawal. Publishing contests to DeDi would fix it and is refused for a stronger reason: a public log of disputed claims is a public record of which workers are in dispute (#68).

Withdrawal is the single central fact about credentials: a Bitstring Status List per deployment, maintained by the credential substrate (the verification service since 2026-08-27, #137; Certify when the Inji path is wired, #130), one bit meaning "still stands" and carrying nothing else. The list is unlinkable bulk data by design: a verifier fetches the whole thing, so checking one credential reveals nothing about which one was checked.

This section used to say "no credential register exists", and that was not true of the built system. The built system has stored every issued credential in full since the confirmation service was written — the signed document, the claim it came from, and the subject reference — and serves it at GET /v1/credentials/{id} (owned by confirmation until #137 moved the store to verification, 2026-08-27). Settled 2026-08-24 (#91): a deployment-local credential store is accepted, and its consequence is stated here rather than denied.

The consequence is that the deployment operator holds a complete, permanent copy of every credential every worker has been issued. A verifier still learns nothing extra — the status list’s unlinkability is untouched — but the operator is not a verifier, and a design that says the copy does not exist cannot reason about who may read it. Two things follow, and they are owed rather than optional: the store needs an access boundary (it has none today, because CREST has no caller identity at all — #89), and it needs a retention position, because "forever" is a choice nobody has yet made deliberately. What is retained is also what makes two promises §3 already carries work at all: Certify re-fetch for a worker who loses their phone, and the printed card (§5), which has to be rendered from a credential somebody still holds.

10 · The payments boundary

CREST never holds or moves money. The infrastructure commitment is precisely two contracts:

  • Outbound — the payment trigger: on claim acceptance (confirmed or auto-confirmed), if a rate exists in the linked payment set-up, emit a PaymentInstruction (event_id, worker payment handle, amount/currency, mode) to the configured rail connector. Rails are L2 configuration; the instruction shape is L1.
  • Inbound — the confirmation intake: rails report outcomes into the CompensationRecord (event_id, amount, mode, payment_ref, status PENDING/PAID/DISPUTED, date). Reconciliation compares instructed vs confirmed; every unmatched amount resolves to one reason with one owner — including the previously ownerless gap, which this design closes: accepted claims with no instruction after the set-up's deadline surface to the project administrator by rule.

The compensation record is linked to the credential only by event_id — the work record is never hostage to the payment system.

12 · Why config and product stay easy

The test of this layer is what building on it looks like. Configuration (L2) becomes pure data: a new project is registry rows (project, grants, definitions, payment set-ups, adapter configs) — no code. A new country is a deployment of the same three substrates plus registry seeding. A new work type is a definition version. A new source system of a known class is adapter configuration. Product (L3) becomes replaceable clients of the API surface below: any worker app, any supervisor tool, any funder dashboard — a deployment may replace all of it and still be CREST, because every rule that matters is enforced beneath the product. And the extensibility claims the strategy note cares about fall out structurally: new use cases (matching, credit, skilling) are new verifiers of existing credentials, not new schemas; federation is a key-custody upgrade, not a data-model change; new credential formats are new projections of the same claim object.

Two findings against the reference itself (#172), recorded here because the reference is the design of record for every screen and these are places it is incomplete rather than places we disagreed with it.

F1 — the rail is identical for both J3 actors. Every p1_* and p2_* frame carries the same five entries: Projects · People & roles · Work definitions · Payment set up · Workers. Only the appbar identity changes. This is a reference decision, not an omission, so the implementation must not invent a role-scoped rail that hides entries: role decides what an entry does, and an entry you cannot act on stays visible and names who can. A missing row reads as a feature that does not exist, which is a lie the console can avoid telling — the same posture as a held payment carrying a reason with an owner. The console screens this implies are specified in docs/design/j3-connective-tissue/ (n1–n5, our design, not the reference's).

F2 — the handover is an authority change with no acknowledgement. p1_3 ("Creating a project, and handing it over") names a Configurator and moves straight to p2_1, where the actor has changed: Peter Otieno signs p1_3, Dr. Alice Mutua signs p2_1. The reference draws only the giving side. A named owner who never agreed is worse than no owner, because the project looks staffed and is not — so ownership acknowledgement is now L1 on Context (§2): naming is a proposal, the named party accepts or declines, a decline records who declined and why and returns the project to the Org Admin's queue rather than deleting anything, and activation is gated on the acknowledgement alongside the deployment's own gates. The trail of answers is append-only, because after a re-handover the current state says PENDING again and "who declined this, and why" is exactly the fact that would otherwise be gone.

Stated residue on the activation gates. The L1 line above says "the two activation gates enforced beneath product — named support contact, and signed work definition before any credential issues". What #172 built is the mechanism: a context declares its readiness conditions by name, each is satisfied at the service's clock, and activation refuses with every unmet condition named rather than with a bare no. The two specific gates are not compiled into it, deliberately — a gate vocabulary is something two deployments could reasonably disagree about — and the second of them is not a project-activation gate at all: "no credential before a signed definition" belongs on the issuance path (§7), which #172 does not touch. So the two named gates are today a deployment's declared gate names plus, for the second, an unbuilt check on a different path. Recorded as a statement rather than left as a discovery.

Batch/aggregate verification unbounded — re-identification risk at small populationsJ9, J11Decided — every batch declares a purpose and is size-capped. The requirement to declare is L1 and not negotiable; the cap itself is L2, because a national payroll run and a three-NGO pilot would reasonably disagree about the number and both are still CREST. An uncapped batch is a bulk export with a purpose string attached, and W8 — a worker can see who checked them — means nothing if one check covers everybody. Refusing a batch endpoint outright was considered and rejected: employers script it anyway, and that is the same disclosure with none of the visibility. The sub-rulings (decided 2026-08-25): a purpose is free text, 10–200 characters, because it ends up in front of the worker in their check trail and a worker should not need a codebook; the cap's L1 default is 100 and a deployment can move it but not remove it — a non-positive value is refused, because a cap that can be configured away is a warning; every credential in a batch writes its own presentation entry, so "who checked me" reads the same whether the check arrived alone or among a hundred; and there are deliberately NO aggregate answers — per-credential verdicts only — which is what dissolves J9/J11's small-population floor problem rather than defending it. Decline-work consequences (and decline history as a scoring signal) undefinedJ7Decided — never recorded. CREST records work that happened; a decline history is a conduct record, and one that would follow a worker between programmes for reasons — illness, care, a funeral — the record cannot hold and should not imply. Nothing in the payment path needs it. Recording it worker-visible-only was considered and rejected: data that exists gets requested, and a visibility rule is one export away from not holding. The engineering consequence is a negative one, which is the kind most easily lost — there is no decline primitive, no decline field on Claim, and adding one is a design change rather than a feature.
Compositability switch-off after workers are live; grant narrowing after go-liveJ3Decided — narrowing binds at submission. The authorization check runs when evidence enters (permits() at ingestion) and nowhere on the confirmation or payment path — which was an accident of construction and is now the rule: work already submitted under a grant confirms, exits and pays after the grant is revoked, because the worker cannot un-perform it; new work is refused at the door. POST /v1/authorizations/{id}/revoke is the narrowing instrument — revoke and grant narrower; there is deliberately no edit, because an edited grant has no record of what it used to allow. Immediate-everything was rejected for stranding performed work unpaid; scheduled-only narrowing was rejected because a grant that must be revoked now cannot wait. Proven by a scenario that asserts both halves against one grant.
