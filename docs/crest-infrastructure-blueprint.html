L1 · The layer that cannot bend

CREST Infrastructure Blueprint

The complete infrastructure-layer design: the objects, registries, contracts and invariants that must hold in every deployment for a decade — specified so that the configuration and product layers become thin, replaceable work on top. Substrate choices: Inji for the credential lifecycle, DeDi for tamper-evident public directories, CREST services for everything that knows about work.

1 · Scope and the L1 test

The actor-journeys model gives the admission test: if two deployments could reasonably disagree about it and both still be CREST, it is not infrastructure. Everything in this document passes that test — it is the set of things that must be identical everywhere so that a credential issued in one country verifies in another, a work definition means the same thing to every adapter, and a worker's guarantees hold regardless of which products a deployment runs.

Three substrates carry it. Inji (Certify, Wallet, Verify, eSignet) is the credential lifecycle — issuance, holding, presentation, verification. DeDi is the directory substrate — every registry whose records are public facts gets tamper-evidence, inclusion proofs, signed checkpoints and witnessing for free. CREST's own services hold what neither knows about: work, evidence, strength, consent, and personal data. Nothing below invents cryptography, wallets, or directory infrastructure.

2 · Object model: primitives and profiles

An earlier draft put Worker, ProjectGrant and CompensationRecord in the core — the payments use case leaking into the layer that must outlive it. The strategy note's own warning applies: Aadhaar did not anticipate Jan Dhan; the core must not anticipate payroll. So the model is now two-tier: eleven generic primitives that know nothing about work or money, and profiles that instantiate them per domain. The generic pattern the primitives encode: a defined activity, an attested event, an owned claim, and trust derived from provenance.

3 · Registry architecture on DeDi

The ten registries split by one criterion: is the record a public fact or personal data? Public facts go on the deployment's DeDi node — append-only, inclusion-provable, checkpoint-signed, witnessable by peer nodes (including the global layer's node, giving cross-border verification a cryptographic rather than institutional basis). Personal data stays in the deployment's private store, in-country, forever.

RegistrySubstrateWhy
Organisations, Terms, QualificationsDeDiA verifier must be able to prove which org held which terms at issuance time — that is exactly an inclusion proof at a log position
Work Definitions (all versions)DeDiImmutability and permanent resolvability of every version are native properties of a transparency log
Skill list, Credential shapes, AdaptersDeDiPublished releases, adopted by deployments; the global node carries the canonical copy, national nodes mirror
Projects (metadata + grants)DeDiA grant is part of the trust chain a verifier walks
Workers, Consent, DisputesPrivate storePersonal data; never leaves the country; never in a log anyone can mirror
CredentialsnowhereDeliberately no register — the worker's wallet is the only complete copy; the status list (§9) is the single central fact

Global vs national. One DeDi node per national deployment, plus one global node holding only: deployment public keys, credential schemas, skill taxonomy, and signed work-definition mirrors (no personal data by construction — nothing personal is ever on any DeDi node). National and global nodes witness each other, so neither can rewrite history unobserved. DeDi-node's current operator-gated onboarding matches the recommended org-onboarding default (§14): governance decisions as log entries.

4 · Identity and the worker record

The worker record is deliberately minimal and the binding deliberately late:

  • Existence: a name and one contact route. No document, no phone, no literacy (W1). Assisted registration writes exactly the same record, marked with the registering agent's identity — it "counts the same" (W2) because there is literally no other kind of record.
  • Identifier: a pairwise, deployment-local did:crest:worker:…. Pairwise so that presenting credentials never leaks a global correlatable identifier (W8).
  • Identity binding: attached only when a credential first requires it, via eSignet as the single L0 interface (national ID / MOSIP / OTP behind one OIDC broker). CREST never talks to a national ID directly and never re-creates identity.
  • Deduplication: candidate duplicates are held, never merged; only the registry custodian merges, only with the worker's confirmation (W4). Merge is a private-store operation that re-points claims; issued credentials are untouched (they reference the surviving DID via a recorded alias).

4.1 · The identity-provider integration contract

"Binds to existing identity infrastructure" has to be a concrete interface, not a slogan. The contract has five parts:

Provider classes, like adapter classes

Identity providers are integrated once per class, configured per deployment — mirroring §8's evidence adapters. Four classes cover the target geographies: eSignet (MOSIP's OIDC broker — the preferred front door wherever a MOSIP or eSignet-fronted national ID exists), MOSIP IDA (direct authentication where eSignet isn't deployed), generic OIDC/eKYC (non-MOSIP national systems, e.g. eCitizen-style portals), and mobile OTP (the floor — proves control of a contact route, not legal identity). A deployment configures one or more providers; CREST core sees only the uniform interface below, never a provider's own API.

What CREST consumes, and what it stores

A binding event consumes a signed assertion and keeps three things only: an opaque subject reference (the provider's pairwise/pseudonymous subject identifier — with eSignet this is a per-relying-party PSUT, so CREST never holds a correlatable national ID), a salted hash of the national identifier for matching (below), and the assertion record (provider, class, assurance method, timestamp, expiry of validity if the provider states one). The raw ID number, biometrics, and demographic payload are never persisted — resolved at binding time, discarded after match. This closes the J12 gap ("whether CREST stores the raw ID number is unresolved"): it does not.

The pairwise partition is the relying party, not the OIDC client — confirmed against a deployed eSignet 1.8.0 (P0 finding E6, make spike-esignet). Two clients registered under one relyingPartyId receive the same subject for the same person; a client under a different one receives a different subject. Two consequences, both settled at registration time and silent if got wrong: every CREST client of a deployment must share one relying-party id, or one worker appears as two people; and two programmes that must not be able to correlate their workers must be registered as different relying parties. CREST requests name and phone_number only — never individual_id, which eSignet does offer (W9).

Identity assurance levels

Every worker record carries a derived identity assurance level, computed like tier strength — from facts, never asserted: IA-3 anchor-verified (biometric or eKYC against a national system), IA-2 document-seen (agent captured an ID document; checksum-valid but not authenticated online), IA-1 contact-verified (OTP on a reachable route), IA-0 asserted (name only, assisted enrolment). IA feeds the confidence score (S-3), duplicate detection (S-2), and — critically — the tier function of §6: Tier 1's stated primary risk is identity mapping error, so a Tier-1 outcome record claimed by an IA-0 worker resolves to a visibly weaker verdict than the same record at IA-3. Assurance and evidence strength stay separate axes; verifiers see both.

Matching: how evidence finds a worker

Source systems send whatever worker-joining identifier they have — national ID, phone, program roster ID. The resolution service (S-1) matches via the salted identifier hashes and registered contact routes, in declared precedence order, and records which key matched and at what confidence on the claim itself — provenance the tier function reads. No match → the unclear queue, never a silent guess. Roster IDs match only through a project-scoped mapping table loaded at project setup (L2 data).

Lifecycle: late binding, re-binding, migration

Binding is monotonic and late (W1): a worker starts at IA-0/IA-1, and attaching an anchor later retroactively upgrades the assurance read of already-issued credentials — no reissuance, because assurance is derived, not stored (same mechanism as J7's retroactive credentialing). Re-binding (new phone, re-issued national ID) appends a new assertion record; history is never rewritten. Anchor migration — a deployment switching providers, the J2 open gap — is now specified: bindings are per-provider records under a stable worker DID, so a new provider is added alongside the old, workers re-bind opportunistically at next authentication, and the old provider's assertions remain valid history rather than orphaned state. Inji Wallet's own activation uses eSignet directly where available; where not, wallet binding rides on the deployment's configured provider via the same interface.

5 · Credential substrate on Inji

One credential type, one schema lineage, everywhere: WorkEventCredential, W3C VC issued by the deployment's Inji Certify over OpenID4VCI, signed with the deployment key (single-key custody per §14/D3 — the specifier/issuer split is structural in the data, cryptographic later if federation demands it).

credentialSubject:
  workerId:       did:crest:worker:…          # pairwise (§4)
  claimId:        urn:crest:claim:…
  workUnitId:     urn:crest:unit:…
  skillCode:      CREST-SKILL:chw.bednet-distribution.v2
  definitionRef:  { urn, version, dediLogIndex }   # provable pin (§3)
  period:         { start, end }
  quantity:       { value, unit }              # unit from the definition
  evidence:                                    # provenance FACTS only (§6)
    sourceClass:    DHIS2 | HCM | COMMCARE | BATCH | SUPERVISOR_ENTRY | WORKER_ASSERTED
    captureMethod:  SYSTEM_RECORD | FORM_ENTRY | SELF_REPORT
    adapterRef:     { urn, version }
  issuerAuthority:  { orgId, qualificationRef, grantRef }  # walkable on DeDi
credentialStatus:   BitstringStatusList entry  (§9)

Holding is Inji Wallet in three modes (mobile app; web at assisted-access points; printed PixelPass QR card from enrolment) — same credential, no custodial wallet service. Presentation is OpenID4VP online and PixelPass QR/NFC offline; the offline payload carries the full signed VC, so a bare scan verifies signature and schema with no network, and proves validity-at-issuance only (status needs signal — accepted, per the journeys' bare-scan semantics). Format: JSON-LD/Ed25519 day one; SD-JWT is the planned selective-disclosure upgrade and the schema above is field-compatible with it.

6 · Trust strength: facts stored, judgement derived

This resolves the contradiction between the concept note ("tier is a first-class property of every credential") and the journeys ("strength is never stored"). The rule, stated as infrastructure:

The credential stores provenance facts. The tier is a pure function, evaluated at presentation time: tier = f(evidence facts, definition@version's evidence-to-tier map, current source-assessment). It is always displayed — to worker and verifier alike — never written.

Consequences that make this the right L1 rule: re-assessing a compromised source system downgrades every affected credential's tier instantly, without reissuance; versioning a definition never strands old credentials (they resolve against their pinned version); no attester can inflate strength by asserting it — strength is derived from how evidence arrived, and transport never affects it. The function f itself is L1 (identical everywhere); the evidence-to-tier mappings are L2 data inside each definition.

7 · Work definition lifecycle

The definition is the object every other component reads, so its lifecycle is infrastructure even though its contents are pure configuration:

  • States: DRAFT → RATIFIED → ACTIVE → SUPERSEDED. Immutable from ACTIVE; every change is a new version; every version resolvable forever (a DeDi log entry, so this is enforced by substrate, not policy).
  • Separation of duties: author ≠ approver on the same version — an L1 rule, enforced in the definition service, not left to product UI.
  • Three faces, one signed record: worker face (plain-language evidence requirements + tier ceiling), platform face (source systems, required fields, outcome unit, tier map, schema pointer), verifier face (authorised issuer references, evidence-to-tier map, specifier signature, timestamp). One record, three projections — never three documents.
  • Payment set-ups link by reference, never embed: a definition is complete and usable with no rate attached, because recognition is a use of its own.

8 · Evidence ingestion contract

CREST absorbs heterogeneity; source systems change nothing. The L1 artefact is the canonical work-evidence record — what every class adapter must emit:

mandatory core:            optional enrichment:
  activity                  geography (coarse only — raw location never stored)
  outcome { value, unit }   beneficiary counts, session metadata,
  workerJoiningIdentifier   supervisor identity, device attestation, …
  period { start, end }
  sourceExposure            # where/how the source exposes this record
provenance (adapter-attached, never source-asserted):
  sourceClass · captureMethod · adapterRef · receivedAt · sourceRecordRef

Rules that cannot bend: adapters are written per system class (one DHIS2 adapter, one CommCare, one HCM, one batch-file), configured per deployment; a record providing only the core is valid Tier-1-capable evidence; the four transports (push API, consent-triggered pull, signed batch, supervised manual upload) never influence strength; provenance is attached by the adapter and validated by the pipeline — whatever the source asserts about its own trustworthiness is ignored. The adapter registry (DeDi) records which adapter versions are recognised, so a verifier can walk evidence back to a known translator.

9 · Consent, confirmation, withdrawal

Consent happens exactly three times, and the three moments are distinct objects, never collapsed:

  1. Enrolment consent — the right to fetch and hold evidence about the worker. Recorded once, revocable; voice recording is a valid capture for non-literate workers.
  2. Issuance confirmation — is the draft record true? Draft credential → notify (SMS/USSD/supervisor-assisted) → confirm, dispute, or auto-confirm at T=7 days. Three parallel routes (self, auto, assisted) all lead to issuance and all release payment; the credential flow can never block payment indefinitely.
  3. Disclosure consent — who may see what, per presentation. Showing the bare QR is itself consent for the non-identifying payload; anything more requires an explicit, scoped, recorded grant naming who asked and why. Enforced by the verification service, recorded in the private consent store.

Withdrawal is the single central fact about credentials: a Bitstring Status List per deployment, maintained by Certify, one bit meaning "still stands" and carrying nothing else. No credential register exists; the list is unlinkable bulk data by design.

10 · The payments boundary

CREST never holds or moves money. The infrastructure commitment is precisely two contracts:

  • Outbound — the payment trigger: on claim acceptance (confirmed or auto-confirmed), if a rate exists in the linked payment set-up, emit a PaymentInstruction (event_id, worker payment handle, amount/currency, mode) to the configured rail connector. Rails are L2 configuration; the instruction shape is L1.
  • Inbound — the confirmation intake: rails report outcomes into the CompensationRecord (event_id, amount, mode, payment_ref, status PENDING/PAID/DISPUTED, date). Reconciliation compares instructed vs confirmed; every unmatched amount resolves to one reason with one owner — including the previously ownerless gap, which this design closes: accepted claims with no instruction after the set-up's deadline surface to the project administrator by rule.

The compensation record is linked to the credential only by event_id — the work record is never hostage to the payment system.

11 · Invariants: W1–W10 as enforced mechanisms

The worker guarantees are the acceptance tests of this whole layer. Each maps to a mechanism above — if a mechanism disappears, its guarantee names what breaks:

W1–W2 exist without document/phone/literacy; assisted counts the same → minimal worker record, late identity binding, voice consent, agent-marked same-shape record (§4, §9)
W3 work recorded without a device → evidence arrives from source systems and supervisors, never requires worker hardware (§8)
W4 found next campaign → dedup held-never-merged + custodian merge with worker confirmation (§4)
W5–W6 can see what was done, owed, and why things bounced → confirmation window with stated reasons; compensation record readable by its subject (§9, §10)
W7 provable to a stranger in a minute, offline → full signed VC in PixelPass QR/NFC, printed card path (§5)
W8 proving work ≠ surrendering identity → pairwise DIDs, non-identifying bare-scan payload, scoped disclosure consent, SD-JWT roadmap (§4, §5, §9)
W9 keeps everything when the employer ends → wallet holds the only complete copy; no credential register; Certify re-fetch always available (§3, §9)
W10 a reachable person looks at problems → dispute record is L1; a project cannot activate without a named support contact (gate lives in the project registry, not in product)

12 · Why config and product stay easy

The test of this layer is what building on it looks like. Configuration (L2) becomes pure data: a new project is registry rows (project, grants, definitions, payment set-ups, adapter configs) — no code. A new country is a deployment of the same three substrates plus registry seeding. A new work type is a definition version. A new source system of a known class is adapter configuration. Product (L3) becomes replaceable clients of the API surface below: any worker app, any supervisor tool, any funder dashboard — a deployment may replace all of it and still be CREST, because every rule that matters is enforced beneath the product. And the extensibility claims the strategy note cares about fall out structurally: new use cases (matching, credit, skilling) are new verifiers of existing credentials, not new schemas; federation is a key-custody upgrade, not a data-model change; new credential formats are new projections of the same claim object.

15 · Scope map: the twelve journeys

Every screen journey in the Actor Journeys document (17 Aug), mapped to what it demands of this layer. Format per journey: what L1 must provide (build scope), what is pure L2 data, what stays L3 product. The journeys name an S-1…S-25 taxonomy of automated system services; those map onto the six API boundaries of §13 and are noted where the screens invoke them. Journey-specific open points are consolidated in §16.

J1 · Onboarding an organisation G-2 · 11 screens

L1: org self-registration write + searchable listing; versioned terms catalogue; terms-request → evidence upload → approval state machine; external business-register lookup; key issuance with one-time reveal, withdrawal/reissue (never reinstatement); project→org invitation object carrying a scoped grant (functions × places × period) with accept/decline; role assignment gating whether granted functions are live. L2: the published terms sets and their document requirements; approval-queue routing; sector/country taxonomies. L3: the register/browse/request/invitation screens.

J2 · Setting up the instance G-1 · 8 screens

L1: Instance object as the DeDi log root (name, jurisdiction, residency, languages); one-time binding to the Layer-0 identity anchor (S-4 via S-1); instance-level consent floor that no project may loosen (S-12); first-organisation admission; notification delivery (S-25). L2: the actual consent-rule values, anchor choice, language list, DPO appointment. L3: the guided setup wizard.

J3 · Setting up a project P-1 + P-2 · 24 screens

L1: project/role/grant objects with terms-as-ceiling semantics; the five independent compositability switches as first-class project state; adapter framework bindings (source-system pull and finance-system pull); spreadsheet template generation pinned to a definition version with row-level conformance and partial accept/hold; validation routing (S-8/S-9); the two activation gates enforced beneath product — named support contact, and signed work definition before any credential issues (S-5). L2: every switch value, sourcing mode, intake schedule, payment posture, role invitations, partner grants, finance codes. L3: the console wizards and dashboards.

J4 · Defining the work P-3 · 28 screens

L1: definition registry with sector/counting-basis/category/unit/tier-ceiling structure; publish as two linked signed records (Work Definition + Payment Set-Up) under one signature, mirrored globally; dry-run execution against live records that writes nothing; adapter registration and binding per definition version; tier-ceiling enforcement (a credential can never exceed its source's ceiling); author ≠ approver; ratification-with-pending-fields and delegate alerts; extension-field namespacing. L2: taxonomies, tier acceptance rules, mapping templates, rates/tranches/deductions, delegation rules. L3: the authoring console.

J5 · Payment, and putting it right F-1 + F-2 · 15 screens

L1: Rate as a versioned, effective-dated object separate from the definition; PaymentInstruction emission with idempotency per validated event (S-16); rail-connector interface with sandbox/live separation and a test-transaction lifecycle; reconciliation-file ingestion matched on instruction reference (S-24); account/beneficiary validation (S-18); retry/exception queue (S-23); per-instruction status tracking (S-22). L2: rates, pathway choice (advisory vs instruction+rail), rails, batching/triggers, dispute holds, reconciliation cadence. L3: rate publishing and rail-connection wizards.

J6 · Registering a worker in the field W-2 · 5 screens

L1: offline-first registration queue reconciling into single identities on sync (S-1); scan-or-manual ID capture validated against the anchor when reachable; duplicate detection with confidence scoring, hold-never-merge, custodian-only authority (S-2/S-3); voice consent as a stored audio artefact bound to agent + timestamp (S-12); DID issuance + wallet provisioning feeding on-the-spot card printing (S-10). L2: consent scripts per language, pathway assignment, reprint policy, custodian routing. L3: the supervisor Android field app.

J7 · A worker, end to end W-1 · 22 screens

L1: layered consent ledger (enrolment / per-credential / per-verification); T=7 confirm/dispute/auto-confirm state machine with a 14-day issuer response defaulting in the worker's favour; 2-of-3 social recovery with recovery-contact nomination; selective-disclosure share objects with per-field consent, time-limited links, and a worker-visible audit log; aggregate earnings view across projects with held-payment reason attribution; retroactive credentialing — attaching an identity document later upgrades already-validated work into issuable credentials. L2: tier ceilings, validation mode, payment posture, accepted document types. L3: the wallet app/USSD experience itself.

J8 · From attestation to credential W-4 + P-10 · 8 screens

L1: attestation/correction accepted as evidence with original + correction both retained (S-11); batch roster close producing per-worker events, never merged records, with SMS dispute windows; scoped expiring request links for external institutions whose returns enter the same intake path; issuance on acceptance with no human signature — the org signs. L2: whether a manual validator step exists per project; window lengths; batch pathway enablement. L3: mostly outside CREST — the delivery platform's own supervisor UI and the institution's web template.

J9 · Checking a credential V-1 + V-2 · 6 screens

L1: pass issuance (name + reachable contact, no account, no vetting); disclosure-level resolution = min(verifier accreditation ceiling, worker-granted fields); refusals rendered as explicit values, never silent omission; status-list check at read time with offline freshness timestamp; batch verification jobs with per-row asynchronous worker consent; no-worker-data receipts; check audit trail visible to the worker. L2: accreditation levels and per-level field ceilings; consent-required field lists; batch limits. L3: pass sign-up and institutional check consoles.

J10 · When something stalls W-3 + W-5 · 6 screens

L1: five-key worker lookup with confidence ranking (QR, phone, national ID, biometric, fuzzy name+DOB+district); payment trace exposing rail state read-only — support can escalate, never retry or release money; escalation handoff object with SLA; SMS 2-of-3 recovery protocol issuing a new key, invalidating the old, preserving credential history. L2: SLAs, routing targets, nominee thresholds, message templates. L3: support console and SMS reply interface.

J11 · Seeing where it stands P-2 + V-4 + G-4 · 12 screens

L1: the metrics contracts are infrastructure objects, not report queries — straight-through funnel with per-stage counts, ages, and an owning role per stuck cause; tier-mix tagged capped-by-source vs fell-short with a ceiling-changed flag; the payment-delay taxonomy with every reason bound to a role; registry coverage computed as payable (verified ID + valid payment details) against an external universe estimate; duplicate-merge protocol with the monitored invariant merges_without_worker_confirmation = 0; reuse/freshness aggregation distinguishing verified update from re-save. L2: thresholds/targets, assignment routing. L3: the three consoles (project, funder portfolio, custodian) are views over the same metric objects.

J12 · Systems CREST does not own EXT · 4 screens

L1: the four boundary contracts — identity assertion consumption (anchor → S-1 binding, creating a record if none); the class-adapter contract (one per system class, all deployments) plus a manual add path for unmapped sources; one payment instruction per validated work unit out to a rail with status read-back and reconciliation; and account-free verification — trust carried entirely by the credential signature, so a next employer needs no CREST relationship at all. L2: field mappings (a registry-maintainer judgement, not automatic), schedules, failure-alert thresholds, withholdable fields. L3: the four illustrative external screens.
