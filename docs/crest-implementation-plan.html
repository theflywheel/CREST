From blueprint to running pilot

CREST Implementation Plan

Five phases from substrate spike to pilot-ready deployment, sequenced so every risk is retired by the cheapest artefact that can retire it. Companion to the CREST Infrastructure Blueprint; section references (§) point there.

0 · Approach

  • Substrates before services. Inji, DeDi and eSignet carry the unforgeable properties; prove them against reality in weeks 1–2, before any CREST code depends on assumptions about them.
  • Schemas before code. The eleven primitives, the payments profile and the strength function are executable specification (§14's definition of done). They are the contract every service builds to, and writing them exposes design errors at document cost, not refactor cost.
  • One vertical slice before breadth. The first running system is a single thread — CSV in, credential in a wallet out — through every layer. Breadth (more adapters, more rails, dashboards) attaches to a proven spine.
  • Decision gates on the critical path, explicitly. Three team decisions block later phases; they are scheduled as deliverables, not left to be discovered.

1 · The phases

Phase 0 — Substrate spike weeks 1–2

Retires: "does the stack actually do what the docs say?"
  • Stand up Inji Certify + Wallet + Verify (docker-compose). Issue a hand-authored WorkEventCredential over OpenID4VCI; hold it in Inji Mobile; print it via PixelPass; verify the printed QR fully offline.
  • Stand up a DeDi node (existing Railway path). Publish a sample work-definition record; fetch it with an inclusion proof; version it and confirm both versions resolve.
  • eSignet sandbox: complete one OIDC binding round-trip; confirm the pairwise subject identifier behaviour §4.1 assumes.

Exit: a recorded 10-minute demo of issue → hold → offline verify, plus a short findings memo on anything Inji/DeDi did not do as assumed (feeds Phase 1 schemas).

Phase 1 — Specification bundle weeks 1–5, parallel

Retires: design errors, at document cost. This is §14's definition of done for the layer.
  • Eleven primitive schemas + Trusted Payments profile (roles, LinkedRecord types) as versioned JSON Schemas.
  • Canonical work-evidence record + adapter contract (incl. source heartbeat / expected-volume watermark from gap register).
  • Strength function f as executable spec with test vectors (§6), including identity-assurance interaction (§4.1).
  • WorkEventCredential schema live in Certify; Bitstring Status List configured.
  • Six OpenAPI stubs (§13); identity-provider interface (§4.1) as the seventh contract.
  • One fully-worked definition: bednet distribution, three faces, tier map — resolvable on the Phase-0 DeDi node.

Gate G1 (week 4) — decisions ratified: tier semantics (§6), org onboarding option, key custody, external-institution evidence tier, batch-verification caps, recovery override. One working session, minuted into the blueprint.

Phase 2 — Core loop vertical slice weeks 4–10

Retires: integration risk across every layer. Unlocks journeys J2, J3 (minimal), J4, J6, J8.
  • registry service v0: instance, org self-registration + terms + approval, worker records with assisted enrolment, duplicate hold queue. Public records on DeDi, PII in the private store.
  • definitions service v0: author → ratify (author ≠ approver enforced) → ACTIVE on DeDi; three-face rendering.
  • evidence pipeline with the batch/CSV adapter first (unblocks every source system immediately): canonical record validation, unit + claim creation, identity matching via hashed keys, unclear queue.
  • confirmation service: draft → SMS notify → confirm / dispute / auto-confirm at T=7 → Certify issuance; supervisor-assisted route.
  • Assisted enrolment path end-to-end: field registration, voice consent artefact, DID, printed card.

Gate G2 (week ~10) — the slice demo: a real CSV from a real source system in; seven days (compressed) later, a signed credential in a wallet and on a printed card, offline-verifiable. This is the demo that earns partner conversations.

Phase 3 — Payments profile + verification weeks 9–16

Retires: money-movement and trust-resolution risk. Unlocks J5, J9, J12; J7 substantially complete.
  • payments runtime: rate objects, PaymentInstruction emission with idempotency, one rail connector (mobile money) with sandbox → live separation, CompensationRecord intake, reconciliation with owned reasons — including the cleared-but-never-instructed deadline rule.
  • verification service: wraps Inji Verify; strength function live; DeDi trust-chain walk; pass issuance; per-request disclosure consent with refusals-as-values; check audit trail visible to the worker.
  • Worker experience v1 (app + SMS): wallet, confirmation window, earnings view with held-payment reasons.

Exit: accepted claim → money confirmed on a sandbox rail → reconciliation report with every gap owned; a stranger with a pass verifies a printed credential.

Phase 4 — Inclusion, oversight, federation weeks 15–24

Retires: pilot-scale operational risk. Unlocks J1 (full), J10, J11; hardens J7.
  • USSD/WhatsApp worker channels; dispute + support flows with escalation objects and SLAs; 2-of-3 social recovery (with whatever override G1 decided).
  • Second adapter class (DHIS2 or DIGIT HCM — pick by pilot partner) connected through configuration, proving the class-adapter claim.
  • Metric contracts as objects (§15/J11): straight-through funnel, delay taxonomy, payable coverage, merges_without_confirmation = 0 monitor; the three consoles read them.
  • Global DeDi node + witness ring with the national node; SD-JWT selective disclosure behind a flag.

Gate G3 (week 24) — pilot readiness: W1–W10 walked as acceptance tests against the running system; security review of key handling and PII boundaries; data-protection sign-off on consent artefacts; one partner org onboarded end-to-end without engineering help.

3 · Dependencies that actually bind

  • G1 blocks Phase 2 issuance semantics — tier storage vs derivation must be settled before the credential schema freezes. Everything else in P2 can start regardless.
  • The bednet definition blocks the evidence pipeline — validation needs a real definition to validate against. It is a Phase 1 deliverable for exactly this reason.
  • Rail partner lead time is external — mobile-money sandbox access can take weeks; start the commercial/API conversation in Phase 1, not Phase 3.
  • Pilot partner choice shapes Phase 4 — the second adapter class and the USSD short code both depend on which country/programme pilots. Decide by end of Phase 2.
  • eSignet production access depends on the deployment country's identity authority — the sandbox suffices through G2, but G3 needs the real conversation concluded.
