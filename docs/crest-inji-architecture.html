Architecture starting point · Trusted Payments use case

CREST on Inji

How CREST's five-layer architecture maps onto the Inji stack (Certify, Wallet, Verify) and MOSIP's eSignet — what Inji gives us for free, what CREST must build, and the six decisions to settle before the first line of code.

1 · The one-paragraph shape

Inji is a complete credential lifecycle stack: issue (Certify, over OpenID4VCI), hold (Wallet — mobile and web), present and verify (Verify, over OpenID4VP, including offline QR). That covers CREST's Layer 3 (Wallet) and the credential halves of Layers 2 and 4 almost entirely. What Inji deliberately does not know about is work: it has no concept of a work definition, an evidence adapter, a trust tier, a claim, a dispute, or a payment trigger. That is CREST's actual product surface. The design consequence: CREST is a work-evidence pipeline that terminates in an Inji issuance call, plus a verification service that wraps Inji Verify with trust-chain and strength resolution. We build no crypto, no wallet, no VC plumbing.

3 · The credential itself

One credential type to start: WorkEventCredential, a W3C Verifiable Credential issued by Certify. The subject is the claim (worker ⟷ work unit), not the bare unit — matching the journeys doc's unit/claim split. Sketch of the subject block:

credentialSubject:
  workerId:        did:crest:worker:…      # pairwise per deployment, binds to L0 anchor
  workUnitId:      urn:crest:unit:…        # the unit exists independently
  skillCode:       CREST-SKILL:chw.bednet-distribution.v2
  definitionRef:   urn:crest:def:mw-moh:bednet-dist:v3   # immutable version pin
  period:          { start, end }
  quantity:        { value: 214, unit: "households_visited" }
  evidence:                                 # provenance FACTS, not judgements
    sourceClass:   DHIS2 | HCM | SUPERVISOR_ENTRY | WORKER_ASSERTED
    captureMethod: SYSTEM_RECORD | FORM_ENTRY | SELF_REPORT
    adapterRef:    urn:crest:adapter:dhis2:v1
  issuerAuthority: ref → org registry entry + project grant

Compensation stays out of this credential by design — it's a separate linked record keyed by event_id, exactly as the concept note specifies. The credential must survive a payment dispute untouched.

A tension in your own docs to resolve first. The concept note says the trust tier is "a first-class, visible property of every credential — never a hidden metadata field." The actor-journeys doc says "strength is never stored — it is resolved at the moment somebody asks." These contradict each other. Recommendation: store the facts, derive the judgement. The credential carries immutable provenance facts (source class, capture method, definition version — see evidence above); the verification layer derives Tier 1/2/3 at query time from those facts plus the definition's current evidence-to-tier mapping. The tier is still always visible to worker and verifier — it's just computed, so re-assessing a source system or versioning a definition doesn't strand old credentials with frozen judgements. Both documents' intent survives.

4 · Six decisions to make now

D1 — Credential format: JSON-LD first, SD-JWT for selective disclosure later

Recommend: start with W3C VC (JSON-LD, Ed25519) — Certify's most mature path and what PixelPass offline QR is proven on. Worker requirement W8 ("showing my work doesn't hand over my identity") ultimately wants field-level selective disclosure, which SD-JWT does properly; Certify and Wallet both support SD-JWT, so plan it as a phase-2 format migration rather than a day-1 constraint. Day 1, W8 is approximated with purpose-scoped presentations (OpenID4VP presentation definitions requesting only skill + strength fields).

D2 — The phoneless worker: Inji Web + printed PixelPass card, not a custom wallet

W1–W3 say a worker must exist and be paid with no phone and no literacy. Inji Mobile assumes a smartphone. Recommend: three holding modes, all the same credential: (a) Inji Mobile for smartphone owners; (b) Inji Web accessed at enrolment desks / via the registering agent for assisted access; (c) a printed QR card (PixelPass-encoded, offline-verifiable) issued at registration — the journeys doc already draws "a card printed on the spot." The deployment's Certify instance remains the source the worker can always re-fetch from; no custodial wallet service to build or secure.

D3 — Key custody: one deployment signing key, structural specifier/issuer split in data

Your own open decision (org onboarding O1–O5) notes the first two options "run on a single signing key held by the deployment, which removes the key-custody problem entirely." Recommend: exactly that — Certify signs everything with the deployment key; which organisation issued and which specifier defined the work are registry-backed fields inside the credential, not separate cryptographic signers. Distributed per-issuer DIDs is a later federation step, and the credential shape above doesn't have to change to get there (issuerAuthority becomes a DID reference).

D4 — Identity anchor: eSignet as the single L0 interface

Recommend: CREST never talks to a national ID directly — it talks OIDC to eSignet, which brokers national ID / MOSIP / OTP behind one interface. Assisted enrolment (no document, no phone) creates a worker record on name + one contact route with a deployment-local identifier; the identity binding is attached later, when a credential first needs it — which is what the journeys doc draws ("a document, only when a credential needs one"). Duplicate detection is held-never-merged in the worker registry, outside Inji.

D5 — Revocation without a credential register: Bitstring Status List

The journeys doc is explicit that no central credential register exists, with withdrawal as the single central fact. That is precisely the W3C Status List pattern: Certify maintains a bitstring status list per deployment; a bit says "still stands" and nothing else; verify checks it when online and skips it offline (offline QR proves validity-at-issuance, which the docs already accept for the bare-scan case).

D6 — Work Definition Registry is CREST's crown jewel — build it as its own service

Nothing in Inji models the three-faced work definition (worker face / platform face / verifier face). It's also the object every other component reads: adapters validate against it, the confirm flow renders its worker face, the strength resolver reads its tier mapping, Certify's credential schema pins to it. Recommend: a standalone versioned-and-immutable definition service (ACTIVE versions frozen, new version per change, permanent resolvability of every version), with Certify's schema registry holding only the credential shape and pointing at definition versions by URN.

6 · Suggested build sequence

  1. Phase 0 — Inji spike (1–2 weeks). Stand up Certify, Wallet, Verify with docker-compose. Hand-author one WorkEventCredential schema, issue it to Inji Mobile via OpenID4VCI, print it via PixelPass, verify it offline with Inji Verify. This de-risks the whole VC layer and tests D1/D2 assumptions against reality before any CREST code exists.
  2. Phase 1 — Core loop. Definition service v0 (one definition, one version), worker registry with assisted enrolment, one adapter (pick the batch/CSV adapter — it unblocks every source system immediately), validation engine, confirmation window, Certify issuance. End state: a real evidence file in, a credential in a worker's hand out.
  3. Phase 2 — Payments + verification. Rate/payment set-up, payment trigger with one rail connector (mobile money), reconciliation, verification service with strength resolution and consent, verifier widget.
  4. Phase 3 — Hardening the inclusive paths. USSD/WhatsApp worker experience, dispute/support flows, second adapter class (DHIS2 or HCM), duplicate handling, SD-JWT selective disclosure (D1's second half).

The single most valuable next artefact is the WorkEventCredential schema and one fully-worked work definition (bednet distribution, all three faces, tier mapping included) — because Phase 0 needs the first and every other service is shaped by the second.
