**CREST implementation review — 5 September 2026**

The repository implements a substantial workflow prototype, but it does not yet deliver the reference system’s trust, consent, portability, and payment guarantees. The most serious gaps are executable backend behavior, not visual differences from the journey screens.

**Scope and evidence**

Only these documents were used as requirements:

- [Trusted Payments readout](docs/reference/Copy%20of%20CREST_-Trusted%20Payments%20Use%20Case_Readout_Summary.docx): especially C.2–C.4, D, E, and F.
- [DPI for Livelihoods](docs/reference/Copy%20of%20A%20DPI%20for%20Livelihoods_v1.6.pdf): especially pages 13–16 and 22–26.
- [Actor Journeys](docs/reference/CREST%20%E2%80%94%20Actor%20Journeys_17Aug.html): the model, worker requirements W1–W10, nine flows, and relevant actor screens.

Other documentation, previous gap assessments, generated traceability ledgers, and code comments were not used as authority. Findings follow executable source, SQL, frontend requests, and deployment configuration. Existing uncommitted implementation changes were included as found. No existing files were changed.

This is a repository review, not an inspection of Railway’s current runtime variables, deployed images, network policies, or data residency. Deployment findings distinguish checked-in defaults and workflow behavior from unknown live configuration. No production mutations or exploit requests were made. Missing capabilities mean no implementation was found in the inspected service and application paths; this is not a claim about software outside this repository.

**Actual execution and deployment structure**

Four React applications—worker, field, console, and verifier—call two Go processes through nginx. `core` composes parties, definitions, evidence, and verification; `payments` owns confirmation windows as well as payment instructions. Each core member has a PostgreSQL schema, with transactional outboxes for selected handoffs. Object storage holds consent artefacts. DeDi supports publication of public registry facts. An additional eSignet → Mimoto/Inji → Certify path issues wallet credentials through a Java data-provider plugin.

The primary credential path is:

`CSV upload → evidence unit + worker claim → outbox → payments window → claim acceptance → core credential issuance → payment-release outbox → instruction → configured RAIL_URL`.

This structure is directly established by [services/core/main.go:19](/Users/techsavvyash/sweatAndBlood/flywheel/CREST/services/core/main.go:19), [pkg/service/compose.go:49](/Users/techsavvyash/sweatAndBlood/flywheel/CREST/pkg/service/compose.go:49), [services/core/evidence/service.go:29](/Users/techsavvyash/sweatAndBlood/flywheel/CREST/services/core/evidence/service.go:29), [services/payments/exit.go:85](/Users/techsavvyash/sweatAndBlood/flywheel/CREST/services/payments/exit.go:85), and [infra/railway/nginx.apps.conf.template:38](/Users/techsavvyash/sweatAndBlood/flywheel/CREST/infra/railway/nginx.apps.conf.template:38). Ratification trusts `ratifiedByPartyId` from JSON; changing that string bypasses the author/approver comparison. The middleware deliberately allows requests without bearer tokens through to handlers, and nginx forwards these `/v1` routes. An anonymous caller can therefore attempt valid definition/rate mutations under invented actors.
